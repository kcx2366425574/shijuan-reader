## 〇、总体判断

拾卷的工程底子明显好于一般个人项目：书源"声明式数据、不执行远程 JS"的核心安全边界是对的，解析引擎以纯函数 + 依赖注入组织，9 个零依赖测试文件覆盖 core 主路径，缓存普遍带 LRU 上限，阅读器做了目录分页、章节预取与进度节流，包内无 so 库，81 项测试全过。整体完成度对一款自用型阅读器相当高。

**真正需要优先处理的不是"功能不够"，而是三类问题：**

1. **一条完整的供应链攻击链（唯一安全 P0）**：用户可配置更新源 + 下载 APK 无签名/哈希校验即调用安装 + 已声明安装权限。三者叠加可让恶意 APK 以拾卷同等数据权限落地。
2. **在线升级在新 Android 版本上大概率静默失败（兼容 P0）**：安装权限在 Android 8/10/13/14 的行为差异完全未适配，targetSdk 也未显式声明。
3. **两个高频崩溃 P0**：超大章节全量 DOM 渲染导致中低端机 OOM/ANR；深嵌套畸形 HTML 触发递归栈溢出且部分路径未兜底。

产品侧的核心矛盾则是"**已有数据或能力没接好**"：追更新章数算了却没在书架显示、智能识别入口被藏进"高级工具"、搜索点"先看已有结果"后慢源结果永久丢失、详情页目录定位还是旧逻辑——多为几行改动即可打通关键路径。

## 一、功能完整性

### F1｜阅读页无"换源"出口，章节失败即死胡同 `关联 todo #4/#29`
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：书源失效或正文抓取失败时的所有阅读用户，属于"读不了"的阻断场景。
- **触发场景**：阅读器 `fatalError` 只有"返回/重试"，章节错误只有"重试本章"。若当前源已失效，反复重试无效，只能返回 → 详情页 → 换源 → 全网重搜 → 再进阅读，链路极长。
- **改进建议**：在两种错误态加"换个书源"按钮，就地弹出该书已聚合的候选源（`book.vue` 的 `alternateOffers` 已有），或跳详情并自动 `switchSource`；换源后按章名续读（复用 `performSwitch`）。

### F2｜书源体检默认书名硬编码，易误报"书源失效"
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：所有用体检判断书源好坏的用户（书源出问题时必用）。
- **触发场景**：`sources.vue` 中 `testKeyword = '万相之王'` 且每次打开都重置。很多站点不收录这本书，体检第一步"搜索"就失败，用户得到"未通过"结论而误删可用源。
- **改进建议**：默认词改为取自书架书名/搜索历史，或给下拉候选；把"搜索 0 结果"与"规则抽取失败"区分提示——前者应提示"该书源可能不收录此书，换个书名试试"而非判失败。

### F3｜阅读器缺少进度拖拽 / 全书快速跳转条
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：所有阅读用户，翻页/跳章高频；长篇追更用户尤甚。
- **触发场景**：底部 `.reader-progress` 只是 3rpx 只读条（`@tap` 无绑定），想跳到本章中段只能"目录 → 翻页 → 点条目"多步操作。
- **改进建议**：把进度条改成可点击/拖拽的 seek bar：横向拖动 = 章内百分比，配套可展开的"全书章节滑块"；拖拽时浮层显示目标章名，松手跳转并与 `saveProgress` 打通。

### F4｜App 端无法文件 / 网络导入书源，只能粘贴 JSON
- **优先级**：P1　**建议纳入**：后续版本
- **影响范围**：想扩展书源的中高级用户（尤其 Legado 迁移用户）。
- **触发场景**：`sources.vue` 的"选择文件"按钮带 `v-if="isH5"`，App 端不显示；`chooseFile()` 包在 `#ifdef H5` 内。用户在群聊/网盘收到书源 JSON 文件，Android 端只能手动复制整段粘贴。
- **改进建议**：App 端接入文件选择器与"系统分享打开 .json"；至少补一个"从网络 URL 导入书源合集"，与书源订阅打通。

### F5｜书源"可用"状态是假象，误导选源 `关联 todo #29/#37`
- **优先级**：P1　**建议纳入**：后续版本
- **影响范围**：依赖状态标识选源的用户。
- **触发场景**：`discover.vue` 书源状态徽标写死为"可用"；`sources.vue` 的 `state-dot.on` 仅由 `enabled` 决定。站点已失效但仍启用的源依然显示绿色"可用"，用户据此选源后搜不到书。
- **改进建议**：改为三态"未检测/可用/失效"，初值不要默认绿；结合体检结果或 health.json 落库并显示"上次检测时间"。最低限度先把写死的"可用"改成中性的"已启用"。

### F6｜搜索结果无法就地切换来源
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：多源结果场景（几乎每次搜索）。
- **触发场景**：聚合卡片只显示 primary source + "+N 个备选"，点击进详情再点"换源"会重新全网搜同名书，而非从已聚合的 offers 直接选。
- **改进建议**：结果卡片直接展开 offers 列表，选中即携带该 offer 进详情/阅读，避免二次网络请求。

### F7｜书城"不妨试试"推荐词硬编码，与用户/书源无关
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：进入书城未搜索的新用户与闲逛用户。
- **触发场景**：`suggestions = ['神通者','万相之王','斗破苍穹','诡秘之主']` 写死，既不基于搜索历史也不校验书源收录，点了很可能"没有找到这本书"。
- **改进建议**：改为基于搜索历史/书源热门词的动态推荐，或至少标注"热门搜索"并按启用书源实际可搜到的词生成；无结果时给"换一个"入口。

## 二、用户流程

### U1｜冷启动无新手引导，核心概念缺位
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：全部新用户，首次启动必遇，直接决定留存。
- **触发场景**：`App.vue onLaunch` 只做 `ensureSources` + 静默检查。新用户落地书架看到"从一页开始／搜索一本书，或导入你的书源"，但不知道已有 5 个内置源可直接搜，也不理解"书源"是什么、为何搜书要选源。
- **改进建议**：首次启动插入 2–3 屏轻量引导（书源是什么 → 已有内置源可直接搜 → 如何加更多）；空态卡片给明确主按钮"搜一本书"、次按钮"了解书源"，而非让用户在两个抽象动作里猜。

### U2｜追更新章数已算出却未在书架呈现（闭环断裂）`关联 todo #21`
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：所有追更用户，每日高频。
- **触发场景**：`shelf.vue applyRefresh()` 已计算并存储 `newChapterCount`，但 `grid-item` 只渲染 progress%/lastChapter，**没有新章角标**。点"更新"后 toast 说"X 本有新章节"，回书架却看不出是哪几本。
- **改进建议**：封面右上/最新章节行渲染"+N 新章"红点角标，进入阅读或再次点更新后消除；配合下拉刷新形成"提示→点击→读新章→角标清除"闭环。已有数据没接好，改动很小。

### U3｜智能识别 / 导入书源入口被藏进"高级工具"
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：想加书源的所有用户（产品核心差异化能力的可达性）。
- **触发场景**：`sources.vue` 的 `quick-actions`（智能识别网站/导入书源/链接添加）带 `v-if="showAdvanced"`，默认不可见；toast 文案"普通读者可以忽略"进一步劝退。
- **改进建议**：把"智能识别/导入书源"提升为默认可见主操作（这是核心卖点，不是高级功能）；只把"编辑规则/复制 JSON/调试"收进高级区；"高级工具"改名"更多设置"一类中性文案。

### U4｜搜索"先看已有结果"后慢源结果永久丢失 `关联 todo #4`
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：使用多源搜索且点过"先看已有结果"的用户。
- **触发场景**：`discover.vue stopWaiting()` 设 `ignoreLateResults = true`，把 waiting/loading 的源标记为 skipped；此后这些源即使返回也被 `onSourceDone` 忽略，不再回填。用户为省时间点按钮，就永久拿不到这些源的结果。
- **改进建议**：改为"后台继续补全"——点按钮只结束等待态，慢源完成时静默合并进 `groups` 并把徽标从"跳过"更新为结果数；或提供"继续等待剩余 N 个源"入口，保留选择权。

### U5｜详情页目录"定位"只翻页，与已修的阅读器逻辑不一致 `关联 todo #3`
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：通过目录找章节的读者（长篇用户高频）。
- **触发场景**：todo #3 已修 `reader.vue` 的目录定位，但 `book.vue jumpToChapter()` 仍是旧逻辑：只改 `catalogPage` 并 toast"已定位到第 X 章"，既不滚动到目标项也不进入阅读。
- **改进建议**：把 reader 的 `scroll-into-view` + 目标高亮移植到详情页，统一文案"已定位，点击条目开始阅读"，最好提供"定位并直接阅读"双行为。

### U6｜书架点书封进详情而非续读，多一步
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：所有有在读书的用户，每日高频。
- **触发场景**：`shelf.vue` 的 `grid-item @tap = openDetail`，而顶部已有"继续阅读"卡片可直达，两条路径行为不一致。主流阅读器书架点封面默认直接续读。
- **改进建议**：点书封直接进上次阅读位置；把"书籍详情/更新"下沉到已有的长按菜单 `showBookMenu`；或提供设置项让用户选"点击行为=阅读/详情"。

### U7｜书架顶部放大镜跳"全网书城"而非搜书架 `关联 todo #22`
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：书架上书较多的用户。
- **触发场景**：`shelf.vue` 顶部 `round-btn @tap = goDiscover()`。放大镜在书架页的普遍心智是"搜索我书架里的书"，实际跳全网搜索，反直觉。
- **改进建议**：实现书架内搜索后改为就地搜索；短期不做则把图标换成明确的"去书城"文字/图标，避免语义误导。

### U8｜"更新全部"串行刷新，慢且不可中断
- **优先级**：P1　**建议纳入**：后续版本
- **影响范围**：书架有多本书的追更用户。
- **触发场景**：`shelf.vue updateAll()` 用 `for...of` 串行 `await updateBook()`，20+ 本耗时成倍累积，期间无"停止更新"手段，也无法后台执行。
- **改进建议**：并发 3–4（复用 `settings.searchConcurrency`），增加"停止更新"与失败重试入口；结合下拉刷新在 `onShow` 静默触发（与 U2/todo #21 协同）。

## 三、界面体验

### E1｜辅助文字字号普遍过小，可读性差 `关联 todo #17`
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：全体用户，尤其中老年/视力不佳者（阅读 App 主要人群之一）。
- **触发场景**：各页大量 18–21rpx 辅助文字（`source-name` 18rpx、`grid-latest` 19rpx 等），375pt 屏上约 9–10px，明显低于可读下限；而正文支持 14–32px，反差大。
- **改进建议**：全局最小字号提到 22–24rpx，辅助信息不低于 22rpx；提供"大字体模式"或让界面字号跟随系统字体缩放（与 A5 协同）。

### E2｜搜索状态面板搜索完成后常驻，跨次搜索不收起
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：每次搜索后的所有用户。
- **触发场景**：`discover.vue` 状态面板由 `v-if="searching || statuses.length"` 控制，搜索完成 `statuses` 不清空，面板一直占据结果列表上方；`onShow` 回书城还挂着上次搜索的各源状态条，且无收起按钮。
- **改进建议**：搜索完成后提供收起/自动收起；`onShow` 时若非搜索中则折叠面板；结果页把空间优先让给书籍列表。

### E3｜错误文案技术化，直接抛原始错误 `关联 todo #13`
- **优先级**：P1　**建议纳入**：后续版本
- **影响范围**：遇到网络/书源/同步失败的用户。
- **触发场景**：`discover.showStatusDetail` 直接显示 `status.error` 原文；`sources.syncRepo` 失败 modal 拼接技术细节；`book/reader` 错误态显示 `e.message`。普通用户看不懂也不知下一步。
- **改进建议**：建立错误码→友好文案映射，UI 只说"该书源暂时连不上，可换个源或稍后重试"并给下一步按钮；技术细节收进"复制诊断信息"（见 M1）。

### E4｜无障碍（Accessibility）基本缺失
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：视障/读屏用户，以及依赖键盘/焦点操作的用户。
- **触发场景**：全 App 交互元素几乎都是 `<view @tap>`，无 `role="button"`/`aria-label`、无焦点顺序与焦点可见样式；纯图标按钮读屏软件无法播报含义。
- **改进建议**：关键交互元素补 `role`/`aria-label` 与可读文本；图标按钮加"返回""目录"等标签；确保焦点态可见、支持系统字体缩放。优先覆盖底部 tab、阅读器工具栏、搜索与加书架主路径。

### E5｜长按操作无任何视觉提示
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：不熟悉 App 的普通用户。
- **触发场景**：书架书封、书源卡片都支持长按出菜单，但界面没有任何"可长按"暗示，用户不知道还有"移出书架/编辑书源"等功能。
- **改进建议**：首次使用给一次轻量气泡"长按可管理"；或卡片角落加常驻"⋯"图标，点击/长按都能出菜单。

### E6｜阅读进度百分比口径不一致
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：关注进度的读者。
- **触发场景**：书架/详情用 `progressPercent`（基于 chapterIndex/chapterCount），阅读器用 `readingPercent = (chapterIndex + scrollRatio)/total`。同一本书退出后书架百分比与刚才阅读页可能不一致，造成"进度倒退"错觉。
- **改进建议**：统一一套算法与数据源；退出阅读时把 `readingPercent` 写回 `progress.percent`，各页统一读取。

### E7｜搜索历史只能整体清空，不能删单条
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：注重隐私或搜索词较多的用户。
- **触发场景**：`discover.vue clearHistory()` 只有"清空"全部，历史 chip 无单条删除入口；误搜一个词只能全清。
- **改进建议**：历史 chip 增加单条删除（长按或 × 图标），保留"清空"作为批量操作。

## 四、性能与启动速度

### P1｜启动即并发两个 20s 网络请求，拖慢首屏
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：首次启动及每 12 小时后的冷启动，弱网/无网尤甚。
- **触发场景**：`App.vue onLaunch` 触发 `autoCheckUpdate()`、`autoSyncSourceRepo()`，两处 `fetchText` 超时均 20s；虽不阻塞渲染但长期占用网络栈；`ensureSources()` 与 `saveSettings(loadSettings())` 又各做一次同步 storage 读写。
- **改进建议**：把两个检查移到 `onShow` 后延时 3–5s 或首个空闲帧；共享"启动后已检查"标记并错峰；为检查间隔加抖动，避免所有用户同一时刻打 GitHub API。

### P2｜超大章节 / 整本单章全量渲染导致卡顿与内存峰值
- **优先级**：P0　**建议纳入**：短期修复（至少先做长度上限与分批）
- **影响范围**：阅读器全部用户；连载长章、古登堡 `singleChapter` 整本书尤甚，是最高频路径。
- **触发场景**：`reader.vue:54-59` 用 `v-for` 把 `splitParagraphs()` 产出的**所有段落**渲染成 `<text>` 节点，无分页/虚拟列表/长度上限；`getChapterContent` 还可能循环拼接最多 20 页正文。中低端机 Webview 直接白屏/ANR。
- **改进建议**：按可视窗口 + 前后缓冲分批渲染，或引入虚拟列表/回收列表；单章正文设长度上限（如 30 万字）并提示"原文过长，建议分章阅读"；渲染层用分段字符串而非大规模响应式数组。补一条超大正文性能回归测试。

### P3｜请求层无"外部取消"，切章/切词后旧响应回写界面
- **优先级**：P1　**建议纳入**：短期修复 `关联 todo #6`
- **影响范围**：阅读器、搜索、换源、智能识别等所有异步页面。
- **触发场景**：`service.js` 的 `uni.request` 分支无 abort 句柄，`fetch` 分支的 `abortAfter` 仅做超时 abort。从目录跳到第 300 章的网络未回就点"上一章"，旧请求成功后覆盖新章节；`prefetchNext` 的 900ms 延迟请求在离页后仍回写。
- **改进建议**：`requestBytes` 接受 `AbortSignal`；App 端保存 `uni.request` 的 `requestTask` 并暴露 `.abort()`；页面 `onUnload` 取消在途请求，搜索词变化时 abort 旧搜索。补"离页后无回写"测试。

### P4｜GET 请求无重试与弱网退避
- **优先级**：P1　**建议纳入**：短期修复 `关联 todo #6`
- **影响范围**：所有网络请求，弱网场景命中率最高。
- **触发场景**：`fetchText` 全流程无重试；地铁/电梯弱网单次超时即判失败；5xx/429 未处理（503 WAF 已特殊处理但仅一次）。
- **改进建议**：GET + 幂等请求做 2 次指数退避重试（400/800ms）；429 读 `Retry-After`；正文/目录与搜索设不同重试预算；与 P3 的取消信号联动，避免重试期间切页仍回写。

### P5｜分类索引搜索补详情最多 24 本，首搜可能近一分钟
- **优先级**：P2　**建议纳入**：后续版本 `关联 todo #7`
- **影响范围**：使用 `crawl-index` 源（如 yoboi）的用户首次搜索。
- **触发场景**：`enrichIndexItems` 补 24 本详情、并发 4、单本 12s，冷缓存最坏约 72s，快源结果被一起拖住。
- **改进建议**：只补当前可见前 6–8 本并 await，其余通过 `onSourceDone` 增量回填；索引命中结果先返回再后台补全；补详情超时降到 6s。

## 五、崩溃和异常处理

### C1｜深嵌套畸形 HTML 触发递归栈溢出
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：解析引擎全局——`html.js` 的 `walkElements`/`collectText`/`serializeNode`、`selector.js` 的 `visit`、`rule.js` 的 `collectRecursive` 均为递归；`parseHTML` 的 stack 无深度上限。
- **触发场景**：站点改版、被劫持注入或体检抓到上万层嵌套 `<div>` 的畸形页面；建栈成功但后续 `textContent()`/`selectOne()` 递归抛 `RangeError: Maximum call stack size exceeded`，部分路径（如 `extractChapters` 自动识别）未 catch，冒泡到页面白屏。
- **改进建议**：解析阶段限制最大嵌套深度（如 200 层）并截断；核心遍历改显式栈迭代；对外解析/提取入口统一 try/catch 兜底返回空结果 + 诊断。补深嵌套 HTML 单测。

### C2｜本地存储写入全量静默失败
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：`store.js writeJson` 返回 false 但**所有调用方都不检查**；影响书源、书架、进度、设置、搜索历史。离线索引、升级信息、仓库状态同样 catch-ignore。
- **触发场景**：存储写满、权限被系统回收、或 `JSON.stringify` 抛错；用户操作全显示"成功"，重启后书架/进度丢失且无任何线索。
- **改进建议**：`writeJson` 返回结构化结果，关键写入失败时 toast 提示并写诊断日志；对 `getStorageSync` 返回值做容量/类型校验；提供"清理缓存释放空间"入口。

### C3｜短章节（正文 < 20 字）被判空，无法阅读
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：番外、诗歌、插图章、只有一句话的"本章完"章节。
- **触发场景**：`rule.js extractChapterContent` 中 `if (!content || content.length < 20) throw new EmptyContentError()`，正文清洗后不足 20 字直接抛错，用户看到"正文为空，可能被网站反爬拦截"的误导提示，且无法继续下一章。
- **改进建议**：阈值降到 4–8 字或按章名/站点特征放行；空章给"本章正文较短或为空，可继续下一章"的可操作提示。补 5/19/20 字边界测试。

### C4｜网络响应体无大小上限，可打爆内存
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：`service.js requestBytes`（arrayBuffer 全量读入）、`nativeRequestText`（responseText 全量）、缓存写入；同时是安全面（见 S1 相关）。
- **触发场景**：自定义/被污染书源指向返回 GB 级响应的地址，或站点故障返回超大 HTML；解析引擎再建 DOM，直接 OOM。
- **改进建议**：读前检查 `Content-Length`，超阈值（正文 5MB/索引 20MB）抛 `RequestError`；流式累积滚动计数超限即 abort；解析前按字符数截断并提示"响应过大"；把上限写进书源 schema 由 `normalizeSource` 校验。

### C5｜reader.init 中 source 为空的空指针路径
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：`reader.vue init()` 约 :583–650。
- **触发场景**：用户删除书源后本地残留一个 `chapters` 为空的离线缓存；`source.value` 为 null 但 `offlineBook` 存在，绕过 :586 判空进入 `openBook(null,...)`，成功后在 :632 访问 `source.value.id` 抛 TypeError，最终只显示英文异常文案。
- **改进建议**：进 `openBook` 前显式判空 `source.value`，统一走中文 `fatalError`；清理"offlineBook 存在但目录为空"的残留缓存。补该组合状态测试。

### C6｜整本离线缓存全量写放大，易卡顿/写满
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：`download.js persist` 每 25 章把 `chapters` + 全部 `contents` 交给 `saveOfflineBook`；`offline.js` 对同一 payload 执行**两次** `JSON.stringify`。
- **触发场景**：对上千章、每章几十万字的小说"缓存全书"，每 25 章就把几十 MB JSON 全量序列化并整文件重写，主线程长时间阻塞、内存峰值翻倍，存储很快写满；写失败被 catch 后继续，最终状态 partial。
- **改进建议**：改为按章分片存储 + 索引追加，或大幅提高 `saveEvery` 并只在结束/退出时全量写；限制单书缓存体积并提前提示剩余空间。补大书下载耗时/内存基准测试。

### C7｜书源正则规则无回溯防护，可导致 JS 线程卡死（ReDoS）
- **优先级**：P1　**建议纳入**：短期修复（也可随 S4 后续做静态校验）
- **影响范围**：`rule.js applyTransforms`/`applyReplaceRules`、`service.js searchByIndex` 的 `new RegExp(indexBookUrlPattern)`；规则来自用户导入或远程仓库。
- **触发场景**：导入第三方 Legado 书源含 `##(\s*\S+)+##` 之类嵌套量词，作用在几十万字正文上；try/catch 只拦语法错误，拦不住灾难性回溯。非法 `indexBookUrlPattern` 还会直接抛异常使该书源搜索失败。
- **改进建议**：规则导入时做长度/嵌套量词静态校验，超限拒绝并提示；正则应用前对输入长度截断（单次 replace ≤ 50 万字）；`indexBookUrlPattern` 包 try/catch；高风险规则放独立 Worker 或加执行超时。补 ReDoS 样例测试。

### C8｜网络错误分类不一致、WAF 重试能力弱
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`service.js friendlyNetworkError` 仅用于 uni.request fail；native XHR 分支 onerror 固定返回"网络请求失败"；WAF 503 仅重试一次。
- **触发场景**：HTTPS 证书错误、DNS 污染/被墙、代理返回 403 时，App/H5/Node 三端提示文案不一致；Cloudflare 连续两次挑战或 token 格式变化后直接失败。
- **改进建议**：所有请求入口统一走一套错误分类（超时/DNS/TLS/代理/反爬/5xx），保留原始 errMsg 到诊断；WAF 重试做有限退避并给明确提示。

### C9｜目录分页上限导致超长连载章节丢失
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`service.js loadTocChapters` 的 `maxPages = min(100,...)`；`rule.js extractChapters` 上限 5000 章。
- **触发场景**：3000 章的书、目录首页 20 条时 `pageCount` 被钳到 100，只抓约 2000 章，后 1000 章静默丢失，跳章/进度定位与实际不一致。
- **改进建议**：截断时给"目录仅加载前 N 章"可见提示；把上限做成书源可配置并放宽；校验声明总章数与实际抓取数并记入诊断。

### C10｜后台被强杀导致阅读进度丢失
- **优先级**：P2　**建议纳入**：后续版本 `关联 todo #11`
- **影响范围**：`reader.vue saveProgress` 的 2 秒节流窗口 + `onHide/onBackPress/onUnload`。
- **触发场景**：读到深处 App 被系统回收或强制停止，`onHide` 未可靠触发/来不及写，节流窗口内的滚动位置丢失。
- **改进建议**：翻章完成、滚动停止这两个关键节点立即同步写进度（节流仅用于纯滚动中间态）；恢复时对越界 `chapterIndex`/`scrollTop` 做 clamp。补进度恢复边界测试。

### C11｜智能识别最坏耗时超 4 分钟且无取消
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`autodetect.js autoDetectSource`，最多 12 候选 × 12s，另有首页/详情/目录/AMP/正文各 18s。
- **触发场景**：用户输入搜索入口全部失效的站点，界面长时间停在"正在测试搜索入口 N/12"，无总超时、无取消按钮；离页后仍继续请求并回写。
- **改进建议**：设总时限（如 90s）与候选并发试探；提供"停止识别"并在页面卸载时取消 fetch；阶段超时差异化（首页短、正文长）。

### C12｜多书并发下载无全局节流
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`download.js active` Map 仅按 bookId 去重，每本内部 `concurrency:3`；reader 与 book 两页都可发起。
- **触发场景**：详情页对多本书连续点"缓存全书"，网络并发叠加到 6×N，弱网下互相拖垮、内存电量激增，失败率上升。
- **改进建议**：引入全局下载队列（总并发上限 3–4）；非 WiFi 下整本下载二次确认；在"我的"页统一管理下载任务。

### C13｜离线文件写入非原子，异常时破坏已有缓存
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`offline.js plusWrite` 约 :102–115。
- **触发场景**：`entry.remove()` 先删旧文件再 `createWriter` 写新文件；期间存储写满、权限被拒或 App 被杀，旧完整缓存已删、新文件不完整，整本书打不开且无法恢复。
- **改进建议**：改为"写临时文件 → 成功后原子 rename 覆盖"，失败保留原文件；写入失败计入诊断并提示用户。

## 六、Android 版本与设备兼容性

### A1｜安装权限在 Android 8/10/13/14 的行为差异未适配
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：所有走在线升级的用户（与 S1 强耦合）。
- **触发场景**：
  - **Android 8（API 26）起**：引入该权限，安装未知来源需用户授权，仅 manifest 声明不够；
  - **Android 10（API 29）起**：targetSdk ≥ 29 时安装不能用 `file://` Uri，须 `content://` + FileProvider，否则安装失败；
  - **Android 13（API 33）起**：用户必须手动开启"允许安装未知应用"，系统不再自动授予；
  - **Android 14（API 34）起**：对未知来源安装增加最低 targetSdk 等更多限制。
- **改进建议**：安装前跳转 `ACTION_MANAGE_UNKNOWN_APP_SOURCES` 引导用户授权；确认 HBuilderX 基座的 `plus.runtime.install` 是否走 FileProvider，否则改用 DCloud 推荐写法；按 INSTALL 错误码给"请到设置→允许安装未知应用"的具体指引；优先 WGT 策略（不受该权限约束）。

### A2｜targetSdkVersion 未显式声明
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：`manifest.json` 仅配 `minSdkVersion: 21`，无 targetSdk；`.packrc.json` 仅含包名与 androidpacktype。
- **触发场景**：云打包工具链升级导致 targetSdk 漂移；Android 14+ 对低 targetSdk 应用的安装/权限限制逐年收紧，国内商店普遍要求 ≥ 30/33。
- **改进建议**：显式写 `targetSdkVersion`（与基座能力对齐，建议 33 起步并随基座升级）；每次升级后按 Android 8/10/12/13/14 五档真机回归安装与升级流程；在 RELEASE.md 记录基线。

### A3｜minSdk 21 旧 WebView 对现代 CSS/编码 API 支持不完整
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`backdrop-filter: blur`、`env(safe-area-inset-bottom)`、`overrideMimeType` 与 GBK 解码。
- **触发场景**：Android 5.x/6.0 存量机上毛玻璃渲染异常、底部安全区塌陷、XHR overrideMimeType 行为差异导致 GBK 站点乱码。
- **改进建议**：`backdrop-filter` 加纯色降级；`env()` 保留 `constant()` 兜底（已有）并用 `plus.navigator.getSafeAreaInsets()` 补充；GBK 优先走自研 `gbk-table.js` 减少对 WebView 依赖；README 标注"Android 5.x 部分视觉降级"。

### A4｜刘海屏 / 折叠屏 / 平板缺少左右安全区与宽屏排版
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`reader.vue` 固定 `padding: ... 52rpx`；底部仅处理 bottom inset；全 App 无 `onResize` 监听。
- **触发场景**：横屏刘海机内容贴到左侧挖孔；折叠屏展开后阅读区过宽（行长超 40 字）严重损害阅读体验；平板上弹层宽度失控。
- **改进建议**：正文加 `padding-left/right: max(52rpx, env(safe-area-inset-left))`；宽屏（> 700px）正文设 `max-width: 720rpx` 居中；监听 `onResize` 重算 `windowHeight`。

### A5｜字号固定 px，不跟随系统字体缩放
- **优先级**：P2　**建议纳入**：后续版本 `关联 todo #17`
- **影响范围**：`reader.vue textStyle.fontSize = settings.fontSize + 'px'`；全局 28rpx。
- **触发场景**：视障用户在系统调大"字体大小/显示大小"，App 正文仍按固定 px 渲染。
- **改进建议**：读取 `uni.getSystemInfoSync().fontSizeSetting` 缩放系数并在 textStyle 相乘；阅读设置提供"跟随系统"开关；lineHeight 同步调整。

### A6｜immersed 状态栏与主题切换跨页不一致
- **优先级**：P2　**建议纳入**：后续版本 `关联 todo #17`
- **影响范围**：`manifest.json immersed: true, style: dark` 固定；仅 reader 动态改状态栏；所有页面 navigationStyle: custom。
- **触发场景**：夜读主题下返回书架，状态栏仍保持 light 文字色，而书架背景为浅色，图标几乎不可见。
- **改进建议**：把 `applyStatusBar` 提升为全局 mixin/App.vue，在 `onShow` 按当前主题重置；主题设置页改主题时同步生效；退出阅读器显式恢复 dark。

## 七、权限与隐私安全

### S1｜在线升级无签名/哈希校验，且更新源可由用户任意配置
- **优先级**：P0　**建议纳入**：短期修复
- **影响范围**：`update.js downloadAndInstall`（安装无完整性校验）、APK URL 来自 Release assets 或 notes 正则提取、`config.js` 默认指向 GitHub 但"我的"页可改为任意 `manifestUrl`/`repo`；安装权限已在 manifest 声明。**这是全场唯一的完整攻击链。**
- **触发场景**：用户被诱导填入恶意 `update.json`；GitHub 仓库/Release 被劫持；CDN/网络中间人篡改下载；notes 中 `.apk` 链接被伪造；随后静默下载安装任意签名 APK，取得与拾卷相同的数据访问能力（书架、书源、明文 storage）。此外 `force` 字段可由远程 notes 单方面控制强制更新。
- **改进建议**：发布时为 APK 计算 SHA-256 写入 `update.json`/Release notes，下载后强制校验，不一致拒绝安装；校验签名证书指纹；禁止从 notes 正文正则提取 APK URL，只接受结构化 assets；非 HTTPS 源直接拒绝；`force` 不由远程 notes 单方决定；校验文件大小与清单 `size` 一致。与 A1 一并处理。

### S2｜REQUEST_INSTALL_PACKAGES 属高危权限，滥用面应收敛
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：`manifest.json` 全局声明，安装能力仅 `update.js` 一处使用。
- **触发场景**：应用获得该权限后，任何被诱导的更新流程都能安装 APK，与 S1 叠加放大危害；部分商店因此权限拒收或要求说明。
- **改进建议**：先做 S1 完整性校验；评估改为"跳转系统浏览器/应用市场下载"以移除该权限（WGT 热更新不需要）；若保留，在"我的→在线升级"显式告知用途，并仅用户主动点击升级时才走安装流程（当前启动静默检查只打 badge 不安装，这点是对的，应保持）。

### S3｜书源 URL 仅校验协议，缺乏 SSRF / 内网探测防护
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`service.js` 仅校验 `^https?://`；书源 URL、搜索 URL、章节 URL 全部来自用户导入或远程仓库；`fetch: redirect:'follow'` 会跟随到任意地址。
- **触发场景**：用户订阅恶意书源合集，把 `bookUrl`/`nextContentUrl` 指向 `http://127.0.0.1:8080` 或云元数据地址 `169.254.169.254`，App 成为内网探测代理，结果可能通过正文回显。
- **改进建议**：对非用户手动输入的书源做目标地址校验：禁 IP 字面量、loopback、link-local、私网段；fetch 分支检查重定向后 `response.url`；导入时统一校验所有 URL 字段。

### S4｜本地存储全部明文，书源 headers 可能含凭据
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`store.js writeJson` 明文；书源对象含 `headers`（合并进请求）、WAF cookie 由 `plus.navigator.setCookie` 持久化；书架/搜索历史/进度同样明文。
- **触发场景**：设备被物理接触或 root 后读取私有目录；"复制诊断信息"功能若实现不当会泄露书源 token/headers。
- **改进建议**：对含 headers/cookie 的字段单独加密（Android Keystore 派生密钥，H5 降级提示）；诊断信息对 URL 参数与 headers 脱敏；文档明确说明本地数据不加密，避免用户填入敏感凭据。

### S5｜uniStatistics 已关闭，但需核查云打包基座其他上报
- **优先级**：P2　**建议纳入**：短期修复
- **影响范围**：`manifest.json uniStatistics.enable = false`，`modules: {}` 为空——方向正确。
- **触发场景**：DCloud 云打包基座可能默认包含 Crash/统计 SDK，即使 uniStatistics 关闭；隐私政策需如实披露。
- **改进建议**：每次云打包后抓包确认无 `dcloud.net.cn`/统计域名请求；"我的"页增加隐私说明，明确"无账号、无埋点、所有数据仅存本地"；README 法律边界段补数据侧声明。

## 八、包体积

### B1｜静态资源存在约 1.1MB 冗余大图
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：`src/static/icons/app-1024.png` 856KB、`logo.png` 203KB、`favicon.png` 42KB；而 manifest 的 Android 图标实际取自 `unpackage/res/icons/*`。
- **触发场景**：若这三张图未被任何页面引用则白占资源包；即便被"关于"页引用，1024×1024 PNG 也远超展示需要。
- **改进建议**：全仓 grep 确认引用，未引用直接删除；被引用的转 WebP 或 pngquant 压缩（目标 < 100KB）；按展示尺寸提供 2x 图而非原图；H5 构建单独排除 App 专用图标。

### B2｜GBK 码表 72KB 全量内置
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`src/core/gbk-table.js` 被 `charset.js` 静态 import，所有用户（含只读 UTF-8 源）都承担。
- **改进建议**：改为按需动态 import（首次遇到 GBK 响应时加载）；或按常用区裁剪码表并保留降级。对 16MB 包影响有限，优先级低于 B1。

### B3｜16MB 体积大头是 uni-app 基座，JS 引擎已足够精简
- **优先级**：P2　**建议纳入**：后续版本（说明性，无需大动）
- **影响范围**：4 个 release APK 均约 16MB；`modules: {}` 未启用额外原生模块，无 so 库（已确认）。
- **改进建议**：保持 modules 为空，不引入地图/支付/推送等原生 SDK；发布开启资源混淆与 PNG 压缩；用 bundle report 确认无重复依赖。此项属"保持现状即可"。

## 九、代码可维护性

### M1｜大量空 catch 吞错 + 无全局错误处理与诊断信息
- **优先级**：P1　**建议纳入**：短期修复 `关联 todo #13`
- **影响范围**：`service.js` 十余处 `catch(e){}`、store/source-repo/update 的 storage 写入静默失败；`App.vue onError` 仅 console.error；main.js 无 `app.config.errorHandler`。
- **触发场景**：用户反馈"书打不开/白屏"但无任何可排查信息；线上问题无法复现定位。
- **改进建议**：接 `app.config.errorHandler`；建轻量诊断缓冲区（环形队列，记录版本/书源 id/name/URL/stage/错误/时间，脱敏，上限 50–100 条）；"我的"页提供"复制诊断信息"；storage 写失败 toast 提示而非静默。与 C2/E3 协同。

### M2｜版本号分散多处，文档已失真
- **优先级**：P2　**建议纳入**：短期修复
- **影响范围**：`manifest.json` 1.0.4/104、`config.js`、`package.json version` 已是 **1.0.0**（漂移）、README 称"60 项测试"实测 **81 项**、todo #12（CI）实际已完成但仍标 `[ ]`。
- **触发场景**：只改 manifest 忘改 config.js，导致 `getAppVersion()` fallback 与 `checkUpdate()` 比较基准错误，误报或不报更新；文档与现状漂移误导贡献者。
- **改进建议**：建立单一版本源（如 `src/version.js`）由构建脚本生成各字段；CI 加"版本一致性校验"与"测试数量动态描述"；勾选 todo #12、修正 README 测试数。

### M3｜CI 已存在但与 todo 不一致，且缺书源巡检
- **优先级**：P2　**建议纳入**：短期修复 `关联 todo #12/#36/#37`
- **影响范围**：`.github/workflows/ci.yml` 已实现 `npm ci + npm test + npm run build:h5`；companion 书源仓库无夜间巡检；`build:app` 未纳入。
- **触发场景**：贡献者误以为无 CI；书源站点改版后 App 无感知，直到用户报错。
- **改进建议**：勾选 todo #12 消除漂移；在 shijuan-sources 加 `schedule` 定时跑 validate + 联网体检产出 `health.json`；CI 增加版本一致性校验与书源 schema 校验两步；加 `npm run build:app` 编译冒烟。

### M4｜三个超大单文件承担过多职责
- **优先级**：P2　**建议纳入**：后续版本
- **影响范围**：`service.js` 43KB（请求/WAF/缓存/搜索/目录/正文/体检/聚合）、`rule.js` 38KB、`autodetect.js` 33KB。
- **触发场景**：改一处逻辑需通读 1200 行文件；新贡献者上手成本高；单测难按职能拆分。
- **改进建议**：按职责拆 `service.js` 为 `request.js`/`search.js`/`toc.js`/`content.js`/`group.js`，保留 `service.js` 作 re-export 门面避免大范围改动；autodetect 的 6 个 detect 函数拆文件；同步迁移测试。

### M5｜测试 81 项全为纯逻辑单测，关键路径零集成/E2E 覆盖
- **优先级**：P1　**建议纳入**：短期修复
- **影响范围**：9 个测试文件注入 `fetchText`/`globalThis.fetch` mock + 内存 storage，`npm test` 全程 < 1s。空白：uni.request/plus 运行时行为、失败分类/重试/取消、缓存 TTL、WAF 重试、升级安装、plus.io 异常、阅读器/详情页状态机、真机 Webview、多书并发。
- **触发场景**：S1/A1 的安装与校验分支一旦改动无回归保护；异常与边界（深嵌套 HTML、超大正文、GBK 截断、畸形书源、空章节、存储写满）全用正常 fixture，零覆盖。
- **改进建议**：三层补测——①纯逻辑保持；②用假 `uni`/`plus` 对象做服务层集成测试（错误注入）；③真机冒烟清单（冷启动/删源/弱网/断网恢复/长章/整本缓存）写进 docs 并纳入发版检查。为 C1/C2/C3/C7/C9 各补至少 1 个回归测试；引入覆盖率看板（目标 core ≥ 70%）。

### M6｜一个真实代码缺陷未被现有测试发现（正则转义）
- **优先级**：P2　**建议纳入**：短期修复
- **影响范围**：`autodetect.js pickLabeledNode` 约 :159 写成 `new RegExp('(?:'+labels+')\\s*...')`——JS 字符串中 `\s` 退化为 `s`，实际正则是 `(?:作s*者)s*[:：]s*(.+)`（QA 已用 Node 验证正则源码）。
- **触发场景**：详情页标签写作"作 者：张三"（字间有空格）时智能识别取不到作者值。这是"测试只覆盖理想 fixture"的直接后果。
- **改进建议**：改为 `\\s` 并补"带空格标签"识别测试；对自动生成的规则统一做 round-trip 校验（生成规则 → 再解析样页 → 比对字段）。

### M7｜root `type:module` 构建陷阱已有文档但无机器约束
- **优先级**：P2　**建议纳入**：短期修复
- **影响范围**：根目录 `package.json` 无 `type` 字段、`src/package.json` 为 `{"type":"module"}`；README:50 已警告。
- **触发场景**：新贡献者为"规范"给 root 加 `type:module`，导致 `uni is not a function`（CJS 插件被 ESM 加载）。
- **改进建议**：`vite.config.js` 顶部加注释说明；CI 加断言：root package.json 不得含 `type:module`、src/package.json 必须含；CONTRIBUTING 重复警告。
